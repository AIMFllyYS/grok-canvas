# P2–P6 工作站逐 Issue 实施总计划

> 状态：规划与阶段基线发布；P2–P6 尚未完成。本文是原全局规划的执行补充，不修改或替代原计划。
> 执行方法：每次仅取一个叶子 Issue，按 PDCA 和测试先行推进。不要把整份规划交给一个会话连续自由实现。

## 目标、边界与起点

- 目标：保留 React Flow，支持万级混合节点、本地可靠保存、可恢复 Agent 工作流和有界媒体加载。
- 架构：实体文档状态 + 手势投影 + 领域命令 + SQLite DB Worker + 文件媒体 + 增量同步。
- 技术栈：Next.js 16 / React 19 / React Flow 12 / AI SDK 7 / TypeScript / Node / Electron / pnpm。
- 云端仓库仅 `AIMFllyYS/grok-canvas`，集成分支 `feat/workstation-performance`；不向 upstream 提交，不自动合并 main。
- 当前业务基线提交：`5825e780f6c63544910c69458a0acd3120035b35`。此前本地测试 240 项通过、类型检查通过；不是性能或桌面安装验收结论。
- 实际版本由 lockfile、运行时和 CI 日志确定。Node 最低兼容线仍是 package.json 的 22.18；规划 CI 用 Node 22.22.2 和 24.20.0，不能默默提高最低版本。
- 已有：手势保存门控、250ms 坐标检查点、局部渲染订阅、写时复制、引用索引、Agent 放置索引。
- 尚无：实体 store、统一命令/outbox、SQLite、增量订阅、LOD、完整预显示。既有空间网格不是已经完成视口裁剪。
- 数据留本地。GitHub 只存代码、规划、合成测试和脱敏证据，不上传账户、真实画布、媒体、SQLite 或浏览器存储。
- 不自动收费生成、不安装云数据库、不部署应用、不做多人协作、音频/剪辑器或全画布引擎重写。

## 如何读取：给普通模型的最短上下文

1. 读取本页、`protocol.md`，然后定位当前 Issue 的 Task-ID。
2. 读取 `manifest.json` 中该任务的直接依赖；不要只凭编号判断顺序。
3. 只读取对应阶段文档的那个二级章节，以及该章节指定的 `contracts.md` 段落。
4. 读取列出的当前源文件和依赖 Issue 的交接结论。首次出现的新文件均是待创建路径，不是已存在能力。
5. 如果依赖没有合入集成分支、字段签名与契约不一致、或测试基线失败，停在 Plan 阶段报告，不猜接口。
6. 一个 Issue 的 PR 只关闭它自身；父 Issue 不自动关闭。使用 `prompts.md` 中的单任务提示词。

每个任务包都给出 Plan / Do / Check / Act；其中测试输入、预期状态、异常分支和禁止改动均为验收要求，而非可选建议。

## 依赖分析：为什么不能机械地按阶段数字排序

### 主依赖链

```text
G0 → P2-01 → P2-02 → P2-03 → P2-04 → P2-05
                         ├→ P2-08（Agent/异步写入统一）
                         └→ P3-01 → P3-02（三端原生闸门）
P2-05 → P2-06 → P2-07 → P2-09
P2-09 → P6-01（提前做埋点，不等最终验收才测量）
P3-01 → P3-03 → P3-04 → P3-05 → P3-06
P3-04 + P3-02 → P3-07（一致性备份）
P3-06 + P3-07 + P3-02 + P2写入闭环 → P3-08（唯一主库切换）
P3-08 → P3-09 → P3-10
P3同步 + P2空间/手势 → P4显示；P3资产 → P4派生与媒体预算
P3任务/事件 + P2预显示 → P5状态/工具；P4稳定几何 → P5占位接替
P3/P4/P5完成 → P6-02 → P6-03 → P6-04
```

以 manifest 的边为准；上图只帮助理解关键路径。

### 隐含依赖已显式补齐

- 原生 SQLite 的版本/ABI/Worker 资源必须先证明三端可运行，才允许开始真实数据切换。
- `prepare-desktop.mjs` 当前硬编码 `.next`，不能拿隔离 distDir 的旧产物冒充新桌面包；P3-02 负责统一构建根目录。
- 不能只迁移 canvases：Agent 会话、视频任务、生成记录、claims、最后打开画布及旧幂等 IDs 都有迁移归属。
- 客户端恢复/outbox 协议先于主库切换：未确认修改未排空时，不允许维护模式越过它。
- 备份/恢复先于切换，而不是上线后再补。
- 事件必须和正式写入同事务；SSE 不能先发成功再尝试写数据库。
- outbox 安全删除、事件压缩、删除墓碑和迟到重复命令要使用同一水位策略。
- 裁剪之前必须将全选/复制/删除/框选/fit bounds 从可见 DOM 迁到完整文档语义。
- LOD 之前先做媒体预算；只少挂 DOM、但继续预载原图和视频，不能满足资源约束。
- Agent 的 committed 与内容 ready 是不同状态；预显示依赖稳定 ID 和正式增量接替。
- 埋点 P6-01 提前执行；最终 P6-03 使用相同 fixture、硬件、版本与测量方法对比。

## 推荐分批执行顺序

默认只启动一个 Agent，不依赖昂贵模型或并行子代理。每批不是一个大 Issue，也不是要求一个会话完成整批；**每行中的每个 ID 都开独立会话/PR**。

| 批次 | 建议顺序 | 批次退出条件 |
|---|---|---|
| 0 | G0 | 干净云端 checkout 可安装、测试、构建；未手测项登记明确 |
| 1 | P2-01 → P2-02 → P2-03 → P2-04 → P2-05 | 接口、局部更新、冲突、撤销、增量恢复独立测试通过 |
| 2 | P3-01 → P3-02 | 原生驱动的 Node/standalone/Electron 实际运行证据齐全 |
| 3 | P2-06 → P2-07 → P2-08 → P2-09 → P6-01 | 用户/Agent/后台统一写入口，手势/预显示隔离，采样工具可用 |
| 4 | P3-03 → P3-04 → P3-05 → P3-06 → P3-07 | 只在隔离目录完成关系存储、导入和恢复，不切用户主库 |
| 5 | P3-08 → P3-09 → P3-10 | 维护切换、增量同步、水位与裁剪恢复通过故障测试 |
| 6 | P4-01 → P4-02 → P4-03 → P4-04 → P4-05 → P4-06 | 完整图语义不受裁剪影响，媒体/重组件预算可观测 |
| 7 | P5-01 → P5-02 → P5-03 → P5-04 | 真实进度、稳定占位接替、有界工具查询、未知结果恢复 |
| 8 | P6-02 → P6-03 → P6-04 | 故障、实机长稳、干净安装/升级、人工签收齐全 |

理论上 P3-01 与部分 P2 可以并行，P4-01 与查询工具也有独立性。但它们共享 package.json、FlowCanvas、Agent 和数据库入口，默认串行可减少普通模型的冲突和返工。仅隔离目录、独立分支且依赖已满足时才考虑并行；本次不自动派发。

## 范围与退出条件

- G0 是云端复现任务，不把 240 这个历史数字写死为永久测试数。
- P2 退出：普通编辑不靠整图 diff 产生操作；不同字段共存，同字段保护；一次手势一次撤销；预显示无副作用。
- P3 退出：位置修改不读写正文；事务/回执/事件一致；迁移可中断；切换后只有 SQLite 权威；无常态全图轮询。
- P4 退出：完整内容 ≤80、常规投影目标≤400、播放器≤2、默认播放1；万级图的选择和关系仍完整。
- P5 退出：事件真实、终态不丢、失败无残影、成功不重复；未知付费状态不自动重发。
- P6 退出：统一基准下的实测、故障矩阵、长稳证据和人工签收均通过，才可提出主线合并或发布请求。
- 未通过任何一道数据正确性闸门，不能靠调低断言、关闭 foreign_keys 或清空用户数据继续。

## 变更和成本控制

- 已确定 SQLite，不重复数据库选型研究。驱动兼容失败时保留证据停在 P3-02；不可暗中切换驱动。
- 叶子任务不跨越存储切换、协议切换、UI 裁剪三种高风险边界同时修改。
- 同一 Issue 可用多次会话：Plan/测试设计 → 实施 → Check/修正。续接用代码提交、失败用例与日志，不重读全历史。
- 第一次测试失败可按证据修正；同一根因连续三次失败时停止，报告接口或架构冲突。
- 单包超过列定范围或依赖契约需改，先补充本包 Issue 的变更说明与受影响任务；不偷偷发明第二套协议。
- SOTA 额度优先保留给已复现且普通模型无法收敛的冲突/迁移/幂等问题，其余命令执行和证据整理使用普通模型。

## CI 的职责与限制

- `workstation-ci.yml`：干净安装、Node 跨版本/Windows 回归、类型检查、Ubuntu 生产构建和规划脚本测试。
- `workstation-plan.yml`：校验文档/依赖图，发布或幂等更新父子 Issues 与 blocked-by 关系，上传规划与编号映射 artifact。
- 发布器只修改自己 HTML 标记包裹的 Issue 区块；保留人工补充，不重开已关闭 Issue，不创建 PR、不调用模型。
- 普通代码 PR 必须提供单一 Task-ID 与 PDCA 证据；机器可检查格式、依赖关闭和命令回归，不能证明人工截图真实或替代性能验收。
- GitHub 的默认分支仍是 main；合入集成分支后，Issue 未自动关闭时由人工核对 CI/证据后关闭，不通过改默认分支解决。
- Actions artifact 是辅助日志，不能作为永久唯一存档。合成汇总证据写入仓库专用 evidence 目录；真实 trace 由用户保存，不自动公开。
